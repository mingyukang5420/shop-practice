## 실습 기준 교재 대비 도메인 매핑

`practice-guide.zip`(Boot 4.1/Java21 실습 기준 교재)은 Customer/Product를 다루는 일반 리테일 예제다. 이 프로젝트는 도서 쇼핑몰(요구사항명세서 4절 도메인 용어 정리)이므로, 실습서에서 가져온 것은 **구현 패턴(패키지 구조·예외 처리 설계·Entity/DTO 분리 방식)**이고 **도메인 이름과 엔티티 구성은 우리 요구사항을 따른다**. 대응 관계는 아래와 같다.

| 실습서(Customer/Product 도메인) | 이 프로젝트 | 매핑/차이 사유 |
| --- | --- | --- |
| `Customer` (회원가입·로그인·BCrypt·포인트 보유) | `Member` | MVP는 인증(REQ-001~003) 제외, 고정 더미 회원 id=1만 존재(요구사항명세서 2절). 포인트 개념 없음 |
| `Product` (name, price) | `Book` (title, author, category, price, stock, description) | 도서 쇼핑몰 도메인이라 상품 대신 도서. 재고(stock)·카테고리·저자 등 실습서 Product엔 없는 필드 추가 |
| (없음) | `Category` | 실습서엔 카테고리 개념 자체가 없음. 도서 분류(키워드+카테고리 조합 검색, 기능명세서 2.1)를 위해 신규 도입, CRUD API 없이 `data.sql` 시딩만 |
| (없음, Customer-Product를 주문 시 직접 연결) | `CartItem` | 실습서는 장바구니 단계 없이 바로 주문/수량 누적. 우리는 REQ-011/012에 따라 장바구니 담기→주문 전환의 별도 단계가 필요해 신규 도입 |
| (없음, Order 헤더 없이 Customer-Product 직접 매핑) | `Order` | 실습서는 주문을 "고객이 보유한 상품 수량"으로만 관리해 주문 단위 개념이 없음. 우리는 주문 이력 조회(REQ-014)에 주문일시·상태·총액이 필요해 별도 헤더 엔티티로 도입 |
| `OrderItem` (Customer-Product 중간 엔티티, quantity만 보유, 재주문 시 수량 누적) | `OrderItem` (Order 하위, quantity + **주문 시점 title/price 스냅샷**) | 이름은 동일하게 유지. 역할은 확장됨 — 실습서의 OrderItem은 항상 최신 Product를 참조하지만, 우리는 도서 삭제/가격 변경 후에도 과거 주문 내역이 보존되어야 해서(기능명세서 2.5, 4.1) 스냅샷 필드를 추가 |

**반대로 실습서를 그대로 따른 것** — 도메인 이름이 아닌 구조적 컨벤션이라 그대로 채택:

- group/패키지 루트: `com.skala.shop`
- 패키지 구조: `domain/{feature}`에 Entity+Repository 동거, `service`/`controller`/`dto`/`exception`은 최상위 평면 구조
- 예외 처리 클래스 네이밍: `ErrorCode`(enum)/`BusinessException`/`ErrorResponse`(record)/`GlobalExceptionHandler` — 도메인 무관한 공통 인프라라 이름 그대로 사용
- Lombok은 실습서와 달리 계속 사용(사용자 결정, 2단계 진행 중 확정)

## 진행 방식

아래 순서는 하위 계층(엔티티) → 공통 인프라 → 리소스별 API(Book → Cart → Order → Admin) 순으로, 뒤 단계가 앞 단계에 의존하도록 구성했다. 각 단계 완료 시 체크박스를 표시하며 진행한다.

## 0. 프로젝트 기본 설정

- [x] `application.yml`에 H2 인메모리 DB, `spring.jpa.hibernate.ddl-auto`, H2 콘솔(`/h2-console`) 활성화 설정
- [x] 패키지 구조 확정 — `domain/{feature}`(Entity+Repository 같이 배치: book/cart/member/order) + 최상위 평면 `service`/`controller`/`dto`/`exception` (practice-guide.zip 실습 기준 교재 컨벤션)

## 1. 도메인 엔티티 (요구사항명세서 4절 도메인 용어 정리 기준)

- [x] `Member` (더미 회원, id=1 고정 시딩 대상)
- [x] `Category`
- [x] `Book` (title/author/category/price/stock/description)
- [x] `CartItem` (member-book-quantity)
- [x] `Order` / `OrderItem` (OrderItem은 주문 시점 title/price **스냅샷** 필드 보유 — 기능명세서 2.5, 4.1)
- [x] Book 삭제 시 OrderItem의 Book FK가 `NULL` 처리되도록 연관관계 설정 (기능명세서 2.5)

## 2. Repository 계층

Repository는 별도 최상위 패키지가 아니라 **Entity와 같은 `domain/{feature}` 패키지**에 둔다(practice-guide.zip 실습서 컨벤션 — package-by-feature).

- [x] `domain/book/BookRepository` — keyword(title/author) + categoryId 조합 검색 쿼리 (기능명세서 2.1), 향후 `@Lock(PESSIMISTIC_WRITE)` 적용을 고려한 `findByIdForUpdate` 자리 확보(MVP는 미구현, API명세서 7.2 참조)
- [x] `domain/cart/CartItemRepository`, `domain/order/OrderRepository`, `domain/order/OrderItemRepository`, `domain/book/CategoryRepository`, `domain/member/MemberRepository`

## 3. 공통 인프라 (`exception/` 패키지, practice-guide.zip 네이밍 컨벤션 채택)

- [ ] `ErrorCode` (enum) — `HttpStatus`+code+message를 한 항목에 묶어 정의: `BOOK_NOT_FOUND`, `CATEGORY_NOT_FOUND`, `CART_ITEM_NOT_FOUND`, `ORDER_NOT_FOUND`, `INSUFFICIENT_STOCK`, `INVALID_REQUEST`, `VALIDATION_ERROR` (API명세서 6절)
- [ ] `BusinessException` (`RuntimeException` 상속, `ErrorCode`를 받아 던짐)
- [ ] `ErrorResponse` (record: `timestamp/status/code/message/path` — API명세서 1절과 이미 일치)
- [ ] `GlobalExceptionHandler` (`@RestControllerAdvice`) — `BusinessException`/`MethodArgumentNotValidException`(Bean Validation)/`HttpMessageNotReadableException`/일반 `Exception`을 각각 처리해 `ErrorResponse`로 변환
- [ ] 페이징 응답 포맷 (`content/page/size/totalElements/totalPages`) 공통 처리
- [ ] `INSUFFICIENT_STOCK` 메시지에 도서명/요청수량/가용재고 포함되도록 메시지 포맷 구현 (API명세서 7.1)

## 4. 더미 데이터 시딩 (`data.sql`)

## 5. Book API (요구사항명세서 REQ-004~009, API명세서 2절)

- [ ] GET 목록 (keyword/categoryId 필터 + 페이징) — 존재하지 않는 categoryId는 빈 목록(기능명세서 2.1)
- [ ] GET 상세
- [ ] POST 등록 (Bean Validation 적용, categoryId 존재 검증)
- [ ] PUT 수정

## 6. Cart API (REQ-011~012, API명세서 3절)

- [ ] POST 담기 — **동일 도서 재담기 시 수량 합산** + 합산 후 재고 검증(기능명세서 3.1, 차별 기능 1단계)
- [ ] GET 조회 — price/stock은 항상 최신 Book 값
- [ ] PATCH 수량 수정 — 재고 재검증(차별 기능 2단계)
- [ ] DELETE 항목 삭제

## 7. Order API (REQ-013~014, API명세서 4절)

- [ ] POST 주문 생성 — 전체/부분(cartItemIds), 트랜잭션 내 전량 재고 검증 후 전체 성공/전체 롤백(차별 기능 3단계, TOCTOU 재검증)
- [ ] 주문 성공 시 재고 차감 + OrderItem 스냅샷 저장 + 대상 CartItem 삭제
