# 기능명세서 (MVP)

버전: v1.1
상태: 확정
기반 문서: 요구사항명세서.md, 설계_v3(확정), 0731-practice.pdf(구현 패턴 참고)

> **v1.1 갱신**: 12~13단계(작업순서.md)에서 도입한 세션 인증, 포인트 검증(4.1), 주문 취소(4.4)를 반영했다.

## 1. 문서 목적

요구사항명세서의 REQ 항목을 실제 서비스 로직(기능) 단위로 분해하여, 입력값·처리 흐름·비즈니스 규칙·예외 상황을 정의한다. API 요청/응답의 정확한 스키마는 `API명세서.md`를 따른다.

## 2. 도서(Book) 기능

### 2.1 도서 목록 조회 / 검색 / 필터링 (REQ-004~006)

- **입력**: `keyword`(제목/저자 부분일치, optional), `categoryId`(optional), `page`, `size`, `sort`
- **처리 흐름**:
  1. `keyword`가 있으면 title 또는 author에 부분 일치(대소문자 무관)하는 도서만 대상
  2. `categoryId`가 있으면 해당 카테고리로 추가 필터링(위 조건과 AND 결합)
  3. 두 조건 모두 없으면 전체 도서 대상
  4. 결과를 `page`/`size`/`sort`(기본: `createdAt,desc`)로 페이징
- **비즈니스 규칙**: keyword·categoryId는 서로 독립적으로 선택 가능(둘 다, 하나만, 둘 다 없음 모두 유효한 요청)
- **예외**: 존재하지 않는 `categoryId`를 필터로 넘겨도 오류가 아니라 **빈 목록**을 반환한다(카테고리 존재 여부를 검증하지 않음 — 목록 조회는 결과가 없는 것이 정상 흐름이므로)

### 2.2 도서 상세 조회 (REQ-005)

- **입력**: `id`(path)
- **처리 흐름**: id로 조회, 없으면 예외
- **예외**: 대상 없음 → `BOOK_NOT_FOUND` (404)

### 2.3 도서 등록 (REQ-007)

- **입력**: `title`, `author`, `categoryId`, `price`, `stock`, `description`
- **처리 흐름**:
  1. 필수값 검증: `title`/`author` 공백 불가, `price`/`stock`은 0 이상의 정수
  2. `categoryId`가 실제 존재하는 카테고리인지 검증
  3. 신규 도서 저장(생성 시각 자동 기록), 저장된 상세 정보 반환
- **예외**: 필수값 누락/형식 오류 → `VALIDATION_ERROR`(400), 존재하지 않는 `categoryId` → `CATEGORY_NOT_FOUND`(404)

### 2.4 도서 수정 (REQ-008)

- **입력**: `id`(path) + 등록과 동일한 본문
- **처리 흐름**: 대상 존재 확인 → `categoryId` 존재 확인 → 전체 필드 갱신(PUT, 부분 수정 아님) → 수정 시각 갱신
- **예외**: `BOOK_NOT_FOUND`(404), `CATEGORY_NOT_FOUND`(404), `VALIDATION_ERROR`(400)

### 2.5 도서 삭제 (REQ-009)

- **입력**: `id`(path)
- **처리 흐름**: 대상 존재 확인 → 삭제
- **비즈니스 규칙**: 이미 주문된 도서라도 삭제를 막지 않는다. 대신 `OrderItem`이 주문 시점의 도서명·가격을 **스냅샷으로 보관**하고 있으므로, 도서가 삭제되어도 과거 주문 상세 조회(REQ-014)는 정상 동작해야 한다. `OrderItem`이 참조하는 도서 FK는 삭제 시 `NULL` 처리한다(주문 이력의 스냅샷 필드는 영향받지 않음)
- **예외**: `BOOK_NOT_FOUND`(404)

## 3. 장바구니(Cart) 기능

전제(v1.1): 모든 장바구니 기능은 **세션 인증된 로그인 회원**을 기준으로 동작한다. 세션이 없으면(`AuthService.SESSION_MEMBER_ID` 미존재) `UNAUTHORIZED`(401)를 반환한다. (최초 MVP 문서 기준이었던 "고정 더미 회원(id=1)"은 더 이상 자동으로 사용되지 않으며, `dummy`/`dummy1234` 계정으로 로그인해야 동일하게 동작한다.)

### 3.1 장바구니 담기 (REQ-011)

- **입력**: `bookId`, `quantity`(1 이상)
- **처리 흐름**:
  1. 도서 존재 확인
  2. **동일 도서가 이미 장바구니에 있는 경우, 수량을 합산한다**(신규 행을 추가하지 않음) — 이는 설계_v3에 명시되지 않아 본 문서에서 정의하는 규칙이며, 일반적인 이커머스 장바구니 UX와 일치시키기 위함
  3. (기존 수량 + 신규 요청 수량)이 **현재 재고 이하**인지 검증
  4. 검증 통과 시 저장/갱신
- **비즈니스 규칙**: 재고 검증은 합산된 총수량 기준이며, 신규 요청 수량만 따로 비교하지 않는다(장바구니가 실제 구매 가능한 수량 이상을 담아서는 안 되므로)
- **예외**: `BOOK_NOT_FOUND`(404), 합산 수량이 재고 초과 → `INSUFFICIENT_STOCK`(409)

### 3.2 장바구니 조회 (REQ-012)

- **처리 흐름**: 더미 회원의 모든 CartItem을 조회하고, 각 항목의 `price`/`stock`은 **항상 최신 Book 값**을 조회하여 반환(스냅샷 아님 — 아직 주문 전이므로 최신 가격/재고 상황을 사용자에게 보여줘야 함). `totalPrice`는 각 항목의 `price * quantity` 합산

### 3.3 장바구니 수량 수정 (REQ-012)

- **입력**: `itemId`(path), `quantity`(1 이상)
- **처리 흐름**: 대상 CartItem 존재 확인 → 새 수량이 현재 재고 이하인지 검증 → 갱신
- **예외**: `CART_ITEM_NOT_FOUND`(404), 재고 초과 → `INSUFFICIENT_STOCK`(409)

### 3.4 장바구니 항목 삭제 (REQ-012)

- **입력**: `itemId`(path)
- **처리 흐름**: 대상 존재 확인 → 삭제
- **예외**: `CART_ITEM_NOT_FOUND`(404)

## 4. 주문(Order) 기능

전제(v1.1): 4.1~4.2는 **세션 인증된 로그인 회원**을 기준으로 동작한다(미인증 시 401 `UNAUTHORIZED`). 4.3(관리자 조회)은 이전과 동일하게 인증 없이 공개된다.

### 4.1 주문 생성 (REQ-013)

- **입력**: 없음(장바구니 전체 대상) 또는 `cartItemIds`(배열, 부분 주문)
- **처리 흐름** (트랜잭션으로 원자적 처리):
  1. 대상 CartItem 목록 확정: `cartItemIds` 미지정 시 로그인 회원의 전체 장바구니, 지정 시 해당 id들만(로그인 회원 소유가 아니거나 존재하지 않는 id가 섞여 있으면 오류)
  2. 대상이 비어 있으면 오류
  3. **모든 대상 항목에 대해 `quantity <= 현재 재고`를 먼저 검증**한다. 하나라도 재고 부족이면 어떤 것도 반영하지 않고 즉시 실패 처리(전체 롤백)
  4. 재고 검증을 통과하면 대상 항목의 총액(`Σ price × quantity`)을 계산하고, **회원의 보유 포인트가 총액 이상인지 검증**한다(v1.1). 부족하면 어떤 것도 반영하지 않고 즉시 실패 처리
  5. 두 검증을 모두 통과하면 각 항목에 대해: 재고 차감, `OrderItem` 생성(도서명·가격을 **현재 시점 값으로 스냅샷**), `Order` 생성(상태 = "주문완료", `totalPrice` = 항목 합계). 회원의 포인트에서 총액만큼 차감(v1.1)
  6. 주문으로 전환된 CartItem은 장바구니에서 삭제
  7. 생성된 주문 상세 반환
- **비즈니스 규칙**: "전량 실패 시 전체 롤백" — 부분 성공은 허용하지 않는다(설계_v3 명시 사항). 포인트 검증도 동일한 원칙을 따른다
- **예외**: 대상 없음 → `INVALID_REQUEST`(400), 재고 부족 항목 존재 → `INSUFFICIENT_STOCK`(409, 트랜잭션 롤백), 포인트 부족 → `INSUFFICIENT_POINT`(409, 트랜잭션 롤백, v1.1)

### 4.2 주문 목록/상세 조회 (REQ-014)

- **처리 흐름**: 로그인 회원의 주문만 조회(목록은 페이징). 상세 조회 시 주문에 속하지 않는 회원의 요청이면 `ORDER_NOT_FOUND` 처리
- **예외**: `ORDER_NOT_FOUND`(404)

### 4.3 관리자 주문 조회 (REQ-016 백엔드 부분)

- **처리 흐름**: 회원 필터 없이 전체 주문 조회(목록/상세). 세션 인증이 도입된 이후에도(v1.1) 이 엔드포인트는 그대로 인증 없이 공개 상태를 유지한다 — **엔드포인트를 분리**해두어 추후 관리자 권한 체계 도입 시 이 엔드포인트에만 ADMIN 권한 검사를 추가하면 되도록 한다
- **예외**: `ORDER_NOT_FOUND`(404)

### 4.4 주문 취소 (v1.1 신규)

- **입력**: `orderId`(path, `POST /api/orders/{id}/cancel`)
- **처리 흐름** (트랜잭션으로 원자적 처리):
  1. 로그인 회원 소유의 주문인지 확인 → 아니거나 존재하지 않으면 `ORDER_NOT_FOUND`(404)
  2. 이미 취소된 주문(status = "주문취소")이면 재취소를 막는다 → `ORDER_ALREADY_CANCELED`(409)
  3. 주문에 포함된 각 `OrderItem`에 대해, 참조하는 도서가 아직 존재하면(삭제되지 않았으면) 주문 당시 수량만큼 해당 도서의 재고를 복구한다. 도서가 이미 삭제된 경우(FK가 NULL) 재고 복구 대상에서 제외한다(스냅샷만 남아 있으므로)
  4. 회원의 포인트에 주문 총액(`totalPrice`)만큼 환급한다
  5. 주문 상태를 "주문취소"로 변경한다
  6. 갱신된 주문 상세를 반환한다
- **비즈니스 규칙**: 취소는 주문 전체 단위로만 가능하다(항목 단위 부분 취소는 지원하지 않음). 취소된 주문은 재취소할 수 없다
- **예외**: `ORDER_NOT_FOUND`(404), `ORDER_ALREADY_CANCELED`(409)

## 5. 차별 기능 상세: 재고 초과 주문 방지 (REQ-017)

### 5.1 검증 지점 3단계

| 단계 | API | 검증 내용 | 실패 시 응답 |
| --- | --- | --- | --- |
| 1. 장바구니 담기 | `POST /api/cart/items` | (기존 담긴 수량 + 신규 수량) ≤ 현재 재고 | 409 `INSUFFICIENT_STOCK` |
| 2. 장바구니 수량 수정 | `PATCH /api/cart/items/{itemId}` | 신규 수량 ≤ 현재 재고 | 409 `INSUFFICIENT_STOCK` |
| 3. 주문 생성 | `POST /api/orders` | 각 대상 항목의 수량 ≤ 현재 재고 (재검증) | 409 `INSUFFICIENT_STOCK`, 트랜잭션 전체 롤백 |

### 5.2 왜 주문 생성 시점에 재검증이 필요한가 (TOCTOU)

장바구니에 담는 시점과 실제 주문을 생성하는 시점 사이에는 시간 간격이 존재한다. 그 사이 다른 요청(다른 회원의 주문, 관리자의 재고 수정 등)이 먼저 처리되어 재고가 이미 줄어들었을 수 있다. 장바구니 단계의 검증은 사용자에게 즉각적인 피드백을 주기 위한 것일 뿐, **최종 데이터 정합성은 반드시 주문 생성 트랜잭션이 재검증하여 보장**해야 한다(Time-Of-Check to Time-Of-Use 문제).

### 5.3 동시 요청 경쟁 상태 (Lost Update) 시나리오

재고가 1권 남은 도서에 대해 두 개의 주문 생성 요청이 거의 동시에 들어오는 경우:

1. 요청 A, 요청 B가 각각 `stock = 1`을 조회 → 둘 다 "재고 충분" 판정
2. 요청 A가 `stock = stock - 1`(=0) 실행 후 커밋
3. 요청 B도 (이미 낡은 값을 기준으로) `stock = stock - 1`(=0 또는 -1) 실행 후 커밋
4. 결과: 재고 1권에 대해 2건의 주문이 성공 — **초과 판매(overselling)** 발생

MVP의 기본 검증(단순 조회 후 비교)은 이러한 동시 트랜잭션 상황에서 이 문제에 취약하다. 이는 기본 격리 수준(READ COMMITTED 등)에서 "읽고-쓰기(read-then-write)" 패턴이 원자적으로 보장되지 않기 때문이다.

### 5.4 해결 방향 (설계, 차기 라운드 구현 예정)

- 주문 생성 트랜잭션 내에서, 재고 확인·차감 직전에 대상 도서 row에 **비관적 쓰기 락(`SELECT ... FOR UPDATE`, JPA `@Lock(LockModeType.PESSIMISTIC_WRITE)`)**을 건다. 동일 도서에 대한 동시 트랜잭션은 락이 해제(커밋/롤백)될 때까지 대기하게 되어, 순차적으로 검증+차감이 이루어지고 lost update가 방지된다.
- 낙관적 락(`@Version`)도 대안이 될 수 있으나, 충돌 시 재시도 로직이 필요하고 인기 도서일수록 충돌 빈도가 높아져 사용자 경험이 나빠질 수 있어, 재고 차감처럼 충돌 가능성이 높은 케이스에는 비관적 락이 더 적합하다.
- **데드락 회피**: 하나의 주문에 여러 도서가 포함된 경우, 잠글 도서 id 목록을 **오름차순으로 정렬한 뒤 그 순서대로 락을 획득**한다. 모든 트랜잭션이 동일한 전역 순서로 락을 요청하도록 강제하여 순환 대기(교착 상태)가 발생할 조건 자체를 없앤다.
- 상세 API 계약 및 시퀀스는 `API명세서.md`의 "재고 초과 주문 방지 설계" 절을 참조.

### 5.5 MVP와의 관계

MVP 코드에는 5.1의 기본 검증(단순 조회 후 비교, 락 없음)만 구현한다. 5.4의 동시성 강화는 설계까지 완료된 상태로, 실제 다중 회원(인증 도입) 환경이 갖춰진 뒤 구현 우선순위를 재검토한다(현재는 회원이 1명뿐이라 서로 다른 회원 간의 동시 경쟁이 실질적으로 발생하지 않음).
